**主要收益来自恢复接口链路**

同一图片、同一URL与令牌的串行对照中，plus返回500，max返回200并正确识别；max的图片与工具调用往返也通过。官方文档称两者均支持图像理解，因此只能定位为当前plus图片服务/兼容链路故障，不能笼统断言ECNU没有多模态能力。

旧plus失败补跑的HTTP状态计数：{"200": 996, "500": 1841, "504": 2}。新max补跑26题为{"200": 1575, "429": 1}，成功响应比例 **99.937%**，没有500。接口恢复带来了有效输出，比单纯提高并发更关键。

本次流程的不足是最初只验证了文本工具调用，没有先验收完整视频题，随后在持续500的接口上反复全量重试。以后应在全量前固定验证：文本、单图、多图、图像+工具往返、完整视频题。相同错误持续出现时，应先缩小诊断范围，避免无效重跑。

最终配置：文本plus、视频max，任务并发4、请求合计上限2、视频预处理单路。六题阶段曾观察到进程RSS约7.4GiB，随后降到4题。本轮完成说明当前配置可运行，但缺乏连续RSS采样，不能给出严格峰值或宣称内存增长问题已根治。

**评分差异与错误分析**

官方20题失败的首个原因：11题列数不一致、3题行数不一致、6题关系/值不一致。11题列数错误中10题多列、1题缺列。部分题还同时有行数或数值错误，修正列数不保证答案正确。

课程零分9题：task_18, task_85, task_102, task_123, task_129, task_182, task_196, task_300, task_380。task_102的38次API响应全部200，仍得0分。其solver把跨类别重叠的公司数相加为37，而视频已说明原始获奖记录为36条、类别之间有重叠，这是去重和计数推理错误。该0分结果如实保留，没有手工填入正确答案。

task_10、task_86、task_328、task_389官方通过但课程未满分。已核查主要差异是日期字符串，例如预测2022-02-28、gold为2022-02-28 00:00:00。官方按datetime配置归一，课程列匹配未识别为同一列。因此78.90分与66.67%是不同指标，不能互相替代，也不能简单认为官方在所有细节上更严格。

若用通用、符合题意的格式规则解决这4题且不损害其他题，理论上最多再增加约2.75分。这只是分析上限，尚未实施或验证。不能按gold逐题手工修改现有输出；应保存原始结果，以统一程序做独立对照实验。

**后续优化的优先级**

1. 输出契约：严格输出题意要求的列，验证日期、数值单位、排序和重复记录。11题列数问题、4题日期表示差异具有较高的低成本改进价值。增加“去重数量不能超过原始记录数”等通用一致性检查。
2. 推理正确性：重点分析9道零分题的筛选、关联、去重与视频证据使用。优先处理task_300等耗时长但零分的任务，形成通用规则，不为每题编写答案。
3. 视频流水线：26题实际ASR累计32分45秒，截图识别累计11分46秒，抽帧约35秒。视频步骤单路执行，是重要串行开销，但能与其他题的LLM调用重叠，不能直接把这些值当墙钟占比。可考虑在完整输入/模型/参数指纹下复用视频中间产物、复用ASR模型与固定工作线程，或将CPU转写与截图网络识别解耦。首次运行和缓存复跑必须分开报告。
4. 资源与调用效率：当前4题槽位占用较高，继续加并发未必划算。26题补跑约23.73M输入token、0.77M输出token，1576次HTTP响应（含1次重试）。减少投票、重复预处理或上下文长度应单独做质量消融，不能仅以少调用作为优化成功标准。
5. 干净复现：固定60题、源码、模型路由、思考参数、评分器、任务顺序、并发和缓存策略，重新测一次从零运行的总墙钟与内存峰值，条件允许时重复多轮。本次不同模型面对的题目、缓存及并发设置不同，不能据单次修复实验作模型优劣或并发加速的因果结论。
